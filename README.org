* Task Steward RAGE

This repository is the durable control plane for the Task Steward.

It is derived from the StarIntel Labs RAGE template and keeps the RAGE method: *Recursive Analysis with Gated Execution*. Unlike the general template, this repository is intentionally narrow. It stores steward state, knowledge-base facts, expert rules, handoffs, decision history, and the unified Prolog interface used to reason over them.

* Hard boundary

- Only the Task Steward uses this repository.
- External project repositories never import, clone, write, dispatch into, or depend on this repository.
- This repository never stores or vendors code from managed projects.
- Managed repositories are referenced only as external evidence or task targets.
- The Task Steward may mirror observed GitHub state here as facts.
- GitHub Issues in the owning project remain the canonical implementation tasks. This repository stores orchestration state about those tasks, not duplicate task bodies.

* Repository shape

#+begin_src text
state/                 authored policy plus bounded observed/derived steward state
kb/                    Prolog knowledge-base facts
experts/               serial Prolog Mixture-of-Experts rule modules
steward.pl             unified Prolog query/interface surface
.github/workflows/     validation and bounded reconciliation/wake entry points
#+end_src

There is deliberately no =src/= tree for managed projects, no copied implementation code, and no cross-repository runtime dependency.

* State and YAML

YAML is the ergonomic authoring layer for project metadata, handoffs, priorities, policies, and other steward state. YAML may contain validated inline Prolog extension blocks for project-specific facts or rules when the normal schema is not expressive enough.

Inline Prolog is logic-only. It must not gain filesystem, network, process, shell, foreign-library, or arbitrary load/consult authority.

The knowledge base under =kb/= is the Prolog representation consumed by the expert system. Generated facts must remain distinguishable from authored policy.

** Deterministic self-closure

Event delivery is defense-in-depth, not the correctness boundary for Task Steward self-RAGE completion. A steward PR that closes its owning GitHub Issue must stage the post-merge durable state for that issue in the same PR: the task is =closed=, its generation fences any stale owner, and =kb/generated/tasks.pl= is regenerated before exact-head CI.

Only =main= is scheduling-authoritative. A PR branch may therefore encode the state that becomes canonical if and only if that PR merges. When a merge uses =Closes #N=, GitHub closes the canonical Issue as the staged task state lands on =main=, eliminating the one-merge reconciliation lag.

Issue-event, PR-close, scheduled, and manual snapshot reconciliation remain enabled for human or external mutations and drift repair, but steward correctness must not depend on those events firing after a steward-originated mutation.

** Managed GitHub evidence and decisions

Managed-project GitHub state is an observed input, not an LLM scheduling decision. =.github/workflows/managed-reconcile.yml= reads the repositories declared in =state/projects.yml=, normalizes a bounded snapshot into =state/managed_github.yml=, and deterministically compiles that snapshot into =kb/generated/managed_github.pl=.

The reconciler records open issues and pull requests, dependency/readiness labels, severity labels, exact PR head SHAs, exact-head CI state, review decision/thread state when available, timestamps, and exact GitHub source references. API denial, truncation, or incomplete per-PR evidence yields =partial= or =unavailable= evidence. Missing or incomplete evidence is never interpreted as proof that a worker has no work.

=experts/managed_github.pl= combines those observed facts with authored project policy. Explicit user hard stops and paused states win over backlog pressure. Permanent/protected active workers remain retained by policy. An unprotected non-permanent worker may yield only when a fresh complete snapshot proves that no schedulable work remains. Quiet activity by itself is never an abandonment signal.

The same Prolog rules score actionable external work from authored project priority plus observed severity, work kind, CI state, and review state. Existing pull-request repair is preferred over an otherwise equal new issue. Partial snapshots may contribute positive known work, but cannot authorize a destructive yield.

After every managed reconciliation, Prolog exports the authoritative result to =state/managed_decisions.json=. That artifact contains =keep=/=pause=/=yield= for every managed project and the current =next_external= candidate with provenance. It is derived output: CI regenerates it from =steward.pl= and fails if the tracked artifact disagrees.

Managed repositories remain read-only evidence sources. The reconciliation workflow has write authority only for this control repository, and its exact trigger, staging paths, push destination, and shared state-writer concurrency group are fail-closed by =scripts/validate_workflow_scope.py=.

* Serial Prolog MoE

The Mixture of Experts is deterministic Prolog, not an LLM committee. Specialized rule modules execute serially over the same KB and derived facts. Initial expert domains are:

- eligibility
- dependencies
- failure detection
- regression detection
- priority scoring
- job/test skipping policy
- managed GitHub worker retention and external scheduling
- scheduling
- handoffs
- completion gates

LLMs may perform bounded work chosen by the steward, but LLM output never directly determines scheduling, priority, handoff, regression, worker retention, or skip decisions.

* Unified interface

=steward.pl= is the only supported logical interface. GitHub Actions and the Task Steward should query the interface rather than reaching into individual expert modules.

The interface exposes operations such as:

#+begin_src prolog
steward_validate.
steward_next(Action).
steward_next_external(Project, TaskRef).
steward_worker_decision(Project, Decision, Reason).
steward_explain(Action, Explanation).
steward_status(Status).
#+end_src

* Wake model

Workflow validation and logical steward evaluation are separate operations.

- Pull requests and ordinary pushes run validation only.
- A Task Steward empty commit whose message contains =[steward-wake]= may run one logical steward evaluation after validation.
- A workflow/manual dispatch may also request one logical evaluation.
- A state-maintenance commit whose message contains =[steward-state]= is validation-only and may not recursively wake another evaluation.
- A commit containing both markers is invalid and fails closed.

A wake means only "re-evaluate current state". It does not choose the next task. The evaluation calls the unified Prolog interface, and Prolog remains authoritative for the result.

The validation/evaluation workflow has read-only contents permission. State-reconciliation workflows have narrowly bounded write permission only to this repository. They cannot mutate managed repositories, and the scope validator rejects drift in their triggers, staging paths, push destination, or write authority.

* RAGE loop

1. *Analyze*: ingest current steward state and observed evidence.
2. *Gate*: run serial Prolog experts and derive admissible actions.
3. *Execute*: the Task Steward performs only the selected bounded action.
4. *Evaluate*: record result, CI/test evidence, failures, regressions, and handoffs.
5. *Recurse*: wake the steward and reason again from the new state.

Before the expert-system deployment gate is complete, platform task reconciliation is followed by mandatory self-RAGE on this repository even when external work exists. After deployment, external scheduling becomes primary and self-RAGE becomes the fallback when nothing external is schedulable.
